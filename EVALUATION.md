# Evaluation: Dafny, Agda, and Idris2 JavaScript backends

Three dimensions, three tools, three problems each. Versions used:

| Tool | Version | JS flag | Output shape |
| --- | --- | --- | --- |
| Dafny | 4.11.0 | `dafny build --target:js` | one large `.js` file, CommonJS |
| Agda | 2.8.0 | `agda --js --js-optimize` | many `jAgda.<Mod>.js` files + `agda-rts.js`, CommonJS |
| Idris2 | 0.8.0 | `idris2 --cg node` | one self-contained `#!/usr/bin/env node` script |

Compiled-size baseline on factorial (a 30-line program), split into the
user-relevant slice ("solution") and the shipped runtime/stdlib ("library"):

| Tool | source LOC | solution JS | + library JS | = total JS |
| --- | ---: | ---: | ---: | ---: |
| Dafny | 31 | 1,499 | 30,838 | 32,337 |
| Agda  | 40 | 1,565 | 14,926 | 16,491 |
| Idris2 | 22 |  403 |  9,818 | 10,221 |

Idris2 ships the least overhead per program; Dafny the most. Agda's
runtime is the small per-module `agda-rts.js` plus a handful of
`jAgda.Agda.<Builtin>.js` files that are reused across compilations.

## 1. Readability of the emitted JavaScript

### Dafny — readable but encrusted with a runtime

Every Dafny output starts with ~600 lines of `let _dafny = (function() { … })();` containing a hand-rolled runtime: `_dafny.Seq`, `_dafny.areEqual`, char-escape tables, Unicode helpers, a BigNumber-based GCD, etc. After that prelude the user code is recognizable Dafny-shaped JS:

```js
let InsertionSort = (function() {
  let $module = {};
  $module.__default = class __default {
    static Sort(xs) {
      if ((new BigNumber((xs).length)).isEqualTo(_dafny.ZERO)) {
        return _dafny.Seq.of();
      } else {
        return InsertionSort.__default.Insert((xs)[_dafny.ZERO],
          InsertionSort.__default.Sort((xs).slice(_dafny.ONE)));
      }
    };
  };
  return $module;
})();
```

The function names and control flow line up with the source. The noise is the explicit wrapping (`new BigNumber(0)` vs the literal `0`, parenthesizing every receiver). Verdict: **readable but verbose; everything is wrapped in BigNumber and Seq calls.**

### Agda — terse, point-free, deeply curried

With `--js-optimize`, Agda's emitter inlines the constructor tags away and represents `List A` as a flat JavaScript array. The cost is heavily curried arrow chains with single-character names:

```js
exports["sort"] = a => function (x) {
  if (x.length < 1) return Array();
  return exports["insert"](null)(x[0])(
    exports["sort"](null)(x.slice(1)));
};
```

Top-level functions are *named*, but every type-parameter slot becomes a `null` passthrough. The pattern-match compiler emits an immediate `if (x.length < 1) … else …` cascade that's easy to scan. Verdict: **compact and recognizable, but every call site is `f(null)(x)(y)…` and that gets old fast.**

### Idris2 — looks like ordinary, hand-written Node code

`--cg node` produces a single file that reads like the output of a hand-written transpiler:

```js
function InsertionSort_insert(arg1, arg2) {
  switch (arg2.h) {
    case 0: return { a1: arg1, a2: { h: 0 } };
    default:
      const $tcOptName0 = InsertionSort_compare(arg1, arg2.a1);
      switch ($tcOptName0.h) {
        case 0: return { a1: arg1, a2: arg2 };
        default: return { a1: arg2.a1,
                          a2: InsertionSort_insert(arg1, arg2.a2) };
      }
  }
}
```

Constructors collapse to small JS objects with a `.h` tag and `.a1/.a2/...` fields. Function names use a `Module_name` prefix scheme. There's no curried argument boilerplate. Verdict: **the most readable of the three by a comfortable margin.**

## 2. SES (Hardened JavaScript) compatibility

The harness probes four independent things; see `outputs/<problem>/results.json`, `outputs/bundles.json`, and the per-problem docs for raw output.

| Probe | Dafny | Agda | Idris2 |
| --- | :---: | :---: | :---: |
| Static scan for `eval`, `new Function`, primordial mutation, `with`, `__proto__`, etc. | ✅ clean | ✅ clean | ✅ clean |
| `lockdown()` then `require()` the entry file | ✅ pass | ✅ pass | ✅ pass |
| `lockdown()` then `Compartment.evaluate(source)` raw | ❌ require not available | ❌ require not available | ✅ pass |
| `@endo/bundle-source` → `importBundle` into a Compartment | ✅ pass *(with `BigNumber` + `Math` endowed)* | ✅ pass *(default endowments)* | ✅ pass *(default endowments)* |
| Needs bundling? | yes | yes | **no** |
| Compartment endowments required | `console`, `BigNumber`, **`Math`** | `console` | `console` |

**All three tools emit code that survives a SES-locked-down Node process** — no compiler accidentally generates a SES-incompatible idiom in the patterns I scanned for. That's the easy positive answer.

**Raw `Compartment.evaluate` fails for Dafny and Agda** because Dafny calls `require('bignumber.js')` at the top of its emitted file and Agda's per-module emission means every output module does `require('agda-rts')` + `require('jAgda.<Sibling>')`. A SES Compartment doesn't provide `require` by default. This isn't a SES violation in the verified code — it's a packaging problem.

**Idris2 passes raw `Compartment.evaluate` out of the box** because its `--cg node` output is one self-contained file with no `require` at top scope.

### Bundling closes most of the gap — except for Dafny

I ran the Dafny and Agda outputs through `@endo/bundle-source` (Agoric's Endo bundler) and loaded the resulting Endo bundle into a SES Compartment with `@endo/import-bundle`. Both bundle cleanly. The pre-processing required per tool is small enough to inline in `generator/bundle.mjs`:

  - **Dafny:** strip the trailing `Main()` invocation, expose the module-scoped `let`s on `module.exports`, declare `bignumber.js` as a real bundled dependency. *(Bundle succeeds; ~160 KB base64.)*
  - **Agda:** collect all `jAgda.<Mod>.js` files + `agda-rts.js` into one dir, rewrite bare-specifier requires (`require("agda-rts")`) to relative requires (`require("./agda-rts.js")`), strip the trailing `exports.main(...)` side effect. *(Bundle succeeds; ~38–43 KB base64.)*
  - **Idris2:** (didn't strictly need bundling, but tried it for parity) strip the shebang and `try { __mainExpression_0() }` invocation, attach the mangled target symbol to `module.exports`. *(Bundle succeeds; ~15–18 KB base64.)*

The Endo bundles import cleanly for all three tools and the verified `sort` returns the right answer from inside the sealed Compartment. The Agda namespace even exposes all the *types* (`Sorted`, `Order`, `_≤_`, …) alongside the functions, which is a nice property if you wanted to perform additional reasoning in the host.

**Dafny carries one important caveat**: its bundle imports successfully *only* when the Compartment is endowed with `Math` in addition to `BigNumber`. The blocker is `bignumber.js`, which calls `Math.random()` during initialization to seed an RNG that *the Dafny program never uses*. Under SES `lockdown()`, the secure `Math` object on `globalThis` removes `random`. So Dafny→SES integration today has a **mandatory Math endowment** as part of the deployment contract — `new Compartment({ console, BigNumber, Math: hostMath })` rather than just `{ console, BigNumber }`. (The cleanest upstream fix would be a Dafny runtime option to use native `BigInt` instead of `bignumber.js`; that's a Dafny-side change and not in scope here.) Production code should pass a wrapped `Math` (`harden({ ...Math, random: () => 0 })`) rather than the host's, since nothing in Dafny actually consumes the entropy.

### Specific SES gotchas observed

- **Dafny** sets `BigNumber.config({ MODULO_MODE: BigNumber.EUCLID })` at module load. This mutates global state on the imported lib — fine if every Compartment has its own copy (bundling gives you that), surprising if you share `bignumber.js` across tenants.
- **Agda runtime** (`agda-rts.js`) is small (10 KB) and contains no SES-hostile idioms; bundling produces a working compartment-loadable artifact with zero workarounds.
- **Idris2** uses `__lazy`, `__tailRec` etc. as top-level `function`s with no primordial mutation; the Compartment story is the smoothest of the three.

## 3. Interacting with objects defined outside the verified program

This is the "can I `require()` it and call it from a JS host?" question. I ran a concrete probe (`generator/ffi-probe.js`) that hands each compiled `sort` an external JS-side input and reads the output back. All three succeed, but with very different amounts of glue:

### Agda — the only clean call site

```js
const m = require('./jAgda.InsertionSort.js');
const sorted = m.sort([7n, 3n, 5n, 1n, 9n, 2n]);  // BigInt array in / out
```

Top-level Agda definitions land on `module.exports` under their original names (`m.sort`, `m.insert`). Lists round-trip as native JS arrays because `--js-optimize` chose that representation. Naturals are JS `BigInt` because the runtime uses BigInt for `Nat`.

Two caveats: requiring the module *executes its embedded `main`* as a side effect, and the `--js` backend currently has no story for `import` / ESM (only CommonJS).

Foreign imports in the other direction are first-class: `{-# COMPILE JS putStrLn = function (s) { … } #-}` is the equivalent of writing the JS body inline next to a postulate. This is the FFI story I leaned on for the three demos.

### Idris2 — single executable, no module surface

The Node backend produces `build/exec/<name>` ending with:

```js
try { __mainExpression_0() } catch (e) { … }
```

The functions you actually wrote are present in the file (`InsertionSort_sort`, `InsertionSort_insert`, …) but they are not exported — the file is a script, not a module. To call `sort` from external JS today the user has to either:

  (a) read the file as text, strip the trailing main invocation, and evaluate it inside a `new Function(…)` to grab the symbol you want (the ffi-probe does this); or

  (b) use `%foreign "javascript:lambda: …"` to glue Idris2 to outside JS for individual calls, accepting that the overall file is still an executable.

Idris2's planned `%export` extension hasn't landed for the JS codegens at 0.8.0 to my knowledge. Verdict: **strong FFI *in* (`%foreign` is excellent), weak FFI *out* — calling a verified function from a host JS environment requires source-level surgery.**

### Dafny — module-scoped `let`s leak nothing

Dafny's output declares everything as module-scope `let`:

```js
let _dafny = (function() { … })();
let InsertionSort = (function() { … })();
let _module = (function() { … })();
_dafny.HandleHaltExceptions(() => InsertionSort.__default.Main(…));
```

After `require('./InsertionSort.js')` you can't reference `InsertionSort` from the caller — those `let`s are scoped to the module record. The FFI probe works around this by reading the file as text, rewriting `let X =` to `globalThis.X =`, deleting the Main invocation, and `eval()`-ing.

Once you've pierced that, the API is fine: `InsertionSort.__default.Sort(_dafny.Seq.of(...))`. Inputs must be wrapped in `BigNumber` for integer params and in `_dafny.Seq` for sequences; outputs come back the same way and need `.toNumber()` to escape. Dafny has explicit `{:extern}` for FFI in, but the *out* direction (host-call-in) is awkward today.

### Side-by-side: lines of glue per FFI call

From `generator/ffi-probe.js`:

| Tool | Lines of host glue to call `sort([7,3,5,1,9,2])` |
| --- | ---: |
| Agda | 4 |
| Idris2 | 17 (text-patching, list constructor wrappers) |
| Dafny | 14 (text-patching, BigNumber wrapping, Seq wrapping) |

## Bottom line

If the goal is to drop a verified function into an existing JavaScript app — including a SES-locked-down one:

- **Idris2** gives you the most readable JavaScript by a wide margin and is the only one that runs in a SES Compartment out of the box (and through `bundle-source` for parity). The catch is that you can't `require()` it as a library: you get an executable.

- **Agda** has the cleanest module-call surface — `require('./jAgda.Foo.js').myFn(...)` Just Works, lists are JS arrays, the runtime is tiny. It's also the only one with a real two-way FFI story (`{-# COMPILE JS … #-}`). Needs a bundler before it fits in a Compartment, but `@endo/bundle-source` handles it with only the trivial preprocessing in `generator/bundle.mjs` (rewrite bare requires, strip the main side-effect).

- **Dafny** produces the most code per byte of source and the least JS-native output: everything is BigNumber-wrapped, sequences live in their own class, and the top-level uses `let` so the symbols aren't reachable from a host. It runs under `lockdown()` and the Endo bundle imports cleanly into a sealed Compartment *as long as you endow `Math` alongside `BigNumber`* (a quirk of `bignumber.js` calling `Math.random()` at init). A real Dafny→SES integration treats `Math` as part of the deployment contract.

For the specific use case "I want to write a verified library and call it from regular JavaScript (or a SES tenant)": **Agda for the library case, Idris2 for the SES-embedded-evaluator case, Dafny only if you also need its specification language and are willing to write a small wrapper.**

## How to reproduce

```
nix develop          # or have dafny / agda / idris2 / nodejs on PATH
npm install
node generator/build.js       # compile + run every implementation
node generator/ses-check.js   # run SES probes (lockdown+require, Compartment.evaluate)
node generator/ffi-probe.js   # run FFI probes
node generator/bundle.mjs     # @endo/bundle-source + importBundle into Compartment
node generator/report.js      # rebuild docs/<problem>.md
```

Files of interest:

- `problems/<problem>/<tool>/<src>` — the verified sources
- `outputs/<problem>/results.json` — raw build / run / SES JSON
- `outputs/ffi-probe.json` — raw FFI probe JSON
- `outputs/bundles.json` — raw bundle / import-bundle JSON
