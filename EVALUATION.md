# Evaluation: Dafny, Agda, Idris2, and Coq JavaScript backends

A qualitative companion to the autogenerated [`docs/`](./docs/). Four
tools, five shared problems (factorial, reverse, insertion-sort,
vec-zipwith, sum-formula), plus two side explorations under
[`capabilities/`](./capabilities/) (consume/vend FFI patterns per
language) and [`jesc24/`](./jesc24/) (object-capability patterns ported
from agoric-labs/jesc24's HLA proofs).

Versions used (pinned via [`flake.nix`](./flake.nix) + `flake.lock`):

| Tool | Version | JS pipeline | Output shape |
| --- | --- | --- | --- |
| Dafny  | 4.11.0 | `dafny build --target:js`                   | one large `.js` file, CommonJS |
| Agda   | 2.8.0  | `agda --js --js-optimize`                   | many `jAgda.<Mod>.js` files + `agda-rts.js`, CommonJS |
| Idris2 | 0.8.0  | `idris2 --cg node`                          | one self-contained `#!/usr/bin/env node` script |
| Coq    | 8.9.1  | `coqc → ocamlc → js_of_ocaml` (3 stages)    | one self-running closure, no module surface |

Compiled-size baseline on factorial (a ~30-line program), split into
the user-relevant slice ("solution") and the shipped runtime/stdlib
("library"):

| Tool   | source LOC | solution JS | + library JS | = total JS |
| ---    | ---:       | ---:        | ---:         | ---:       |
| Dafny  | 31         | 1,499       | 30,838       | 32,337     |
| Agda   | 40         | 1,565       | 14,926       | 16,491     |
| Idris2 | 22         |   403       |  9,818       | 10,221     |
| Coq    | 26         | 1,624       | 68,794       | 70,418     |

Two stacks dominate the runtime cost: **Dafny** drags in its own
`_dafny` IIFE (~30 KB) plus a `bignumber.js` dep at use sites; **Coq**
inherits the full `js_of_ocaml` runtime (~60 KB) regardless of what
the program does. **Idris2** ships the smallest overhead; **Agda** is
in the middle, with a small `agda-rts.js` + per-module `jAgda.Agda.*.js`
stdlib files reused across compilations.

(All numbers from [`docs/factorial.md`](./docs/factorial.md),
autogenerated. Insertion-sort and sum-formula scale these by similar
factors; see [`docs/insertion-sort.md`](./docs/insertion-sort.md) and
[`docs/sum-formula.md`](./docs/sum-formula.md).)

## 1. Readability of the emitted JavaScript

### Dafny — readable but encrusted with a runtime

Every Dafny output starts with ~600 lines of `let _dafny = (function() { … })();`
containing a hand-rolled runtime: `_dafny.Seq`, `_dafny.areEqual`,
char-escape tables, Unicode helpers, a BigNumber-based GCD, etc. After
that prelude the user code is recognizable Dafny-shaped JS:

```js
let InsertionSort = (function() {
  let $module = {};
  $module.__default = class __default {
    static Sort(xs) {
      if ((new BigNumber((xs).length)).isEqualTo(_dafny.ZERO)) {
        return _dafny.Seq.of();
      } else {
        return InsertionSort.__default.Insert((xs)[_dafny.ZERO],
          InsertionSort.__default.Sort((xs).slice(_dafny.ONE)));
      }
    };
  };
  return $module;
})();
```

Function names and control flow line up with the source. The noise
is explicit wrapping (`new BigNumber(0)` vs the literal `0`,
parenthesizing every receiver). Verdict: **readable but verbose;
everything is wrapped in BigNumber and Seq calls.**

### Agda — terse, point-free, deeply curried

With `--js-optimize`, Agda's emitter inlines the constructor tags away
and represents `List A` as a flat JavaScript array. The cost is heavily
curried arrow chains with single-character names:

```js
exports["sort"] = a => function (x) {
  if (x.length < 1) return Array();
  return exports["insert"](null)(x[0])(
    exports["sort"](null)(x.slice(1)));
};
```

Top-level functions are *named*, but every type-parameter slot becomes
a `null` passthrough. Verdict: **compact and recognizable, but every
call site is `f(null)(x)(y)…` and that gets old fast.**

### Idris2 — looks like ordinary hand-written Node code

`--cg node` produces a single file that reads like a hand-written
transpiler's output:

```js
function InsertionSort_insert(arg1, arg2) {
  switch (arg2.h) {
    case 0: return { a1: arg1, a2: { h: 0 } };
    default:
      const $tcOptName0 = InsertionSort_compare(arg1, arg2.a1);
      switch ($tcOptName0.h) {
        case 0: return { a1: arg1, a2: arg2 };
        default: return { a1: arg2.a1,
                          a2: InsertionSort_insert(arg1, arg2.a2) };
      }
  }
}
```

Constructors collapse to small JS objects with a `.h` tag and
`.a1/.a2/...` fields. Function names use a `Module_name` prefix scheme.
No curried boilerplate. Verdict: **the most readable of the four by
a comfortable margin.**

### Coq — opaque after the OCaml + js_of_ocaml hop

js_of_ocaml mangles every identifier through its optimizer; the
verified `fact` becomes a recursive `function bM(a) { return 0 === a
? 1 : bv(a, bM(a - 1 | 0)); }` somewhere near the bottom of the
70 KB bundle. The repo's per-language extractor in `generator/extract.js`
gives up on symbol-name extraction for Coq and shows the bundle tail
instead. The actual logic is correct (it computes 120 for `fact 5`),
but the JS-to-source mapping is one-way: you can read the Coq, you
can run the JS, but you can't navigate from one to the other without
reading js_of_ocaml's mangling table. Verdict: **the least readable
output of the four — the cost of the two-stage compile is paid here.**

## 2. SES (Hardened JavaScript) compatibility

The harness runs four independent probes per (problem × tool); see
[`outputs/<problem>/results.json`](./outputs/), [`outputs/bundles.json`](./outputs/),
and the per-problem docs for raw output.

| Probe | Dafny | Agda | Idris2 | Coq |
| --- | :---: | :---: | :---: | :---: |
| Static scan for `eval` / `new Function` / primordial mutation / `with` / `__proto__` / etc. | ✅ clean | ✅ clean | ✅ clean | ✅ clean |
| `lockdown()` then `require()` the entry file | ✅ | ✅ | ✅ | ✅ |
| `lockdown()` then raw `Compartment.evaluate(source)` (default endowments) | ❌ no `require` | ❌ no `require` | ✅ | ❌ no `TextDecoder` |
| `@endo/bundle-source` → `@endo/import-bundle` into a Compartment | ✅ (Math endowed) | ✅ | ✅ | ❌ (see below) |
| Needs bundling for SES? | yes | yes | no | no |
| Endowments required for bundled path | `console`, `BigNumber`, **`Math`** | `console` | `console` | n/a (importBundle path fails) |

### All four pass the static scan

No compiler accidentally generates a SES-incompatible idiom in the
patterns we scan for (eval, `new Function`, primordial mutation,
`with`, `__proto__`, etc.). That's the easy positive answer: **the
verified code is not the SES blocker for any of the four**. Every
failure below is in the runtime / packaging, not the user logic.

### `lockdown() + require()` passes for everyone

Inside a Node process that's already had `lockdown()` called, plain
`require()` of the entry file works for all four tools. This is the
most forgiving test — globals are frozen but Node's loader is still
available — and nothing actually breaks at this level.

### Raw `Compartment.evaluate` splits on `require` and on host globals

- **Dafny** and **Agda** fail because their emitted code does
  `require('bignumber.js')` / `require('agda-rts')` / `require('jAgda.X')`
  at the top of the file. SES Compartments don't provide `require`.
  Fixed by bundling.
- **Idris2** passes. Its `--cg node` output is one self-contained file
  with no `require` at top scope (the only `require('process').argv`
  is inside the executable's main, easily avoidable).
- **Coq** fails because js_of_ocaml's runtime reaches for `TextDecoder`
  during init and the default Compartment doesn't expose it. With
  `TextDecoder` + typed-array constructors endowed, this would pass —
  see the Coq-specific note below.

### Bundled-Compartment: Endo's importBundle has its own gotchas

Running the outputs through `@endo/bundle-source` and `importBundle`
gives clean cells for Dafny / Agda / Idris2:

  - **Dafny** bundles successfully if `bignumber.js` is declared as a
    real dependency (so compartment-mapper pulls it in). Import
    requires `Math` endowed because `bignumber.js` calls
    `Math.random()` during init to seed an RNG the program never uses.
    Production code should pass a *wrapped* Math
    (`harden({ ...Math, random: () => 0 })`) rather than the host's.
  - **Agda** bundles successfully after rewriting bare-specifier
    requires to relative ones and stripping the trailing
    `exports.main(...)` side-effect. Default endowments work.
  - **Idris2** bundles successfully even though it doesn't *need* to
    (the single-file output runs fine under raw `Compartment.evaluate`).
    Default endowments work.
  - **Coq** is special. **The Coq bundle does not import via
    `@endo/import-bundle`** because js_of_ocaml's runtime writes
    `globalThis.jsoo_create_file = …` at init, and importBundle creates
    its Compartment with a *non-extensible* globalThis. The
    assignment throws `Cannot add property jsoo_create_file, object is
    not extensible`. This was originally documented as a fundamental
    SES vs js_of_ocaml mismatch; it isn't. A **hand-rolled `new
    Compartment(endowments).evaluate(source)` *does* allow the
    assignment** (its globalThis is extensible), and the Coq bundle
    runs end-to-end there. The blocker is specifically
    `@endo/import-bundle`'s Compartment policy, not `lockdown()`.
    Whether this matters in practice depends on which Compartment-creation
    path your SES deployment uses: the Endo pipeline (importBundle) is
    out; a bespoke compartment evaluator is in.

### Specific SES gotchas observed

- **Dafny** sets `BigNumber.config({ MODULO_MODE: BigNumber.EUCLID })`
  at module load. This mutates global state on the imported lib — fine
  if every Compartment has its own copy (bundling gives you that),
  surprising if you share `bignumber.js` across tenants.
- **Agda runtime** (`agda-rts.js`) is small (10 KB) and contains no
  SES-hostile idioms; bundling produces a working compartment-loadable
  artifact with zero workarounds.
- **Idris2** uses `__lazy`, `__tailRec` etc. as top-level `function`s
  with no primordial mutation; the Compartment story is the smoothest
  of the four. The only friction is the lack of `module.exports`, but
  that's a *modularization* issue, not SES.
- **Coq → js_of_ocaml** requires the most endowments (TextDecoder,
  TextEncoder, the 12 typed-array constructors, ArrayBuffer, DataView)
  *and* runs into importBundle's non-extensible globalThis. Vanilla
  Compartments are happier; importBundle isn't.

## 3. Interacting with objects from outside the verified program

Can the host JS pass a value into the verified function, get a value
back, and have the round-trip survive the language's data
representations? The numbers below are from the matching probe in
[`generator/ffi-probe.js`](./generator/ffi-probe.js):

| Tool   | Lines of host glue to call `sort([7,3,5,1,9,2])` |
| ---    | ---: |
| Agda   | 4 |
| Dafny  | 14 (text-patching, BigNumber wrapping, Seq wrapping) |
| Idris2 | 17 (text-patching, list constructor wrappers) |
| Coq    | n/a — no library surface (see below) |

### Agda — the only clean call site

```js
const m = require('./jAgda.InsertionSort.js');
const sorted = m.sort([7n, 3n, 5n, 1n, 9n, 2n]);  // BigInt array in / out
```

Top-level definitions land on `module.exports` under their original
names. Lists round-trip as native JS arrays because `--js-optimize`
chose that representation. Naturals are JS `BigInt`. Two caveats:
requiring the module *executes its embedded `main`* as a side effect,
and the `--js` backend has no story for ESM (only CommonJS).

Foreign imports the other way are first-class:
`{-# COMPILE JS putStrLn = function (s) { … } #-}` writes the JS body
inline next to a postulate. This is what every demo's `putStrLn` and
the `capabilities/agda/Caps.agda` Counter / Validator are built on.

### Dafny — module-scoped `let`s leak nothing

Dafny's output declares everything as module-scope `let`:

```js
let _dafny = (function() { … })();
let InsertionSort = (function() { … })();
_dafny.HandleHaltExceptions(() => InsertionSort.__default.Main(…));
```

After `require('./InsertionSort.js')` you can't reference `InsertionSort`
from the caller — those `let`s are scoped to the module record. The
FFI probe works around this by reading the file as text, rewriting
`let X =` to `globalThis.X =`, deleting the Main invocation, and
`eval()`-ing.

Once you've pierced that, the API is fine:
`InsertionSort.__default.Sort(_dafny.Seq.of(...))`. Inputs must be
wrapped in `BigNumber` for integer params and in `_dafny.Seq` for
sequences; outputs come back the same way. Verdict: **strong
verification + weak library export.**

### Idris2 — single executable, no module surface

The Node backend produces `build/exec/<name>` ending with
`try { __mainExpression_0() } catch (e) { … }`. The functions you
wrote are present (`InsertionSort_sort`, `InsertionSort_insert`, …)
but not exported — the file is a script, not a module. To call `sort`
from external JS, either:

  (a) read the file as text, strip the trailing main invocation, and
      evaluate it in `new Function(…)` to grab the symbol you want (the
      ffi-probe does this); or
  (b) use `%foreign "javascript:lambda: …"` to glue Idris2 to outside
      JS for individual calls.

`%export` for the JS codegens hasn't landed at 0.8.0. Verdict:
**strong FFI *in*, weak FFI *out*.**

### Coq — no library surface at all

js_of_ocaml's optimizer mangles every identifier (`fact` becomes `bM`)
and wraps the entire bundle in a closure. There's no `module.exports`,
no preserved symbol names, and no clean way to call the verified
function from a JS host without reading the mangling table. The Coq
+ OCaml ports in [`capabilities/coq/`](./capabilities/coq/) and
[`jesc24/*/coq/`](./jesc24/) work around this by *also* writing an
OCaml driver (`driver.ml`) that calls into the extracted module and
prints results; the JS side never sees the verified Coq functions
directly. **Coq output is for executables and end-to-end pipelines,
not libraries.**

### Side-by-side summary

If the goal is "verified library, called from a JS host":

  - **Agda** is the cleanest by a wide margin: `require()` and call.
  - **Dafny** works with a one-shot source patch, then exposes a real
    class-shaped API.
  - **Idris2** needs the same text-patching trick *and* a list
    constructor wrapper, but the resulting glue is short.
  - **Coq** doesn't realistically apply — there's no library surface
    to expose.

## 4. Beyond the mechanized matrix

Two side directories explore patterns that don't fit a 5-problem
4-tool grid:

### [`capabilities/`](./capabilities/) — consume / vend FFI patterns

For each language, two small examples and a writeup:

  - **Consuming a capability** — the verified function takes a
    host-supplied function (a predicate, a logger) and calls it.
  - **Vending a capability** — the verified module returns an opaque
    object (a Counter) that the host holds and operates through.

[`capabilities/dafny/`](./capabilities/dafny/) uses Dafny's verified
classes and proves `Bump` increments `count` by exactly 1.
[`capabilities/idris2/`](./capabilities/idris2/) uses `IORef`.
[`capabilities/agda/`](./capabilities/agda/) uses `postulate + COMPILE JS`.
[`capabilities/coq/`](./capabilities/coq/) uses `Parameter +
Extract Constant` to bind a Coq-typed interface to an OCaml `int ref`;
the validator also gets a real `iff` spec (`validate_iff_forall`).

The per-language READMEs are honest about *where verification stops*:
Dafny verifies the most (it's the only one that proves an invariant
on the vended state machine); the other three rely on the host's
state-privacy primitive (JS closure, IORef, OCaml record field) and
type the interface around it.

### [`jesc24/`](./jesc24/) — object-capability patterns

Ports of operational shapes from
[`agoric-labs/jesc24/theories/heap_lang/lib/`](https://github.com/agoric-labs/jesc24/tree/main/theories/heap_lang/lib).
We don't reproduce jesc24's Iris separation-logic proofs; we just
exercise the runtime shape across the four languages.

  - **[Sealer](./jesc24/sealer/)** — `make_seal` returns `(seal, unseal)`;
    cross-sealer tokens aren't unsealable. Dafny is the only one with
    *compile-time* OCAP enforcement: `Unseal` has `requires b in tbl`,
    so cross-sealer calls don't type-check. The other three rely on
    runtime mechanisms — JS WeakMap (Agda), IORef privacy (Idris2),
    OCaml ref identity (Coq). Idris2's pure-Idris implementation
    actually has a collision case the demo highlights; FFI to a JS
    WeakMap would close it.
  - **[Caretaker](./jesc24/caretaker/)** — revocable forwarder.
    `make_caretaker` returns `{ wrap, enable, disable }`; after
    `disable`, every `wrap` fails. Dafny's `Wrap` has
    `requires enabled` so callers cannot type-check it when the flag
    is provably false; the other three runtime-check.

## Bottom line

If the goal is "drop a verified function into an existing JS app —
including a SES-locked-down one":

- **Idris2** gives you the most readable JavaScript by a wide margin,
  the smallest runtime overhead, and the smoothest SES Compartment
  story (passes raw `Compartment.evaluate`, bundles cleanly under
  importBundle with default endowments). The catch: you can't
  `require()` it as a library — you get an executable. Best
  "embedded-evaluator" target.

- **Agda** has the cleanest library surface — `require('./jAgda.Foo.js').myFn(...)`
  Just Works, lists are JS arrays, the runtime is tiny. The two-way
  FFI (`{-# COMPILE JS … #-}`) is unmatched. Needs bundling for SES
  but the bundle preprocessing is trivial. Best "verified library"
  target. Side-effect-on-import is the one gotcha.

- **Dafny** produces the most verbose JS (everything is BigNumber-wrapped,
  sequences live in their own class) and the worst library export
  story (module-scoped `let`s). But it's the only one that *verifies
  invariants on stateful capabilities* — the Counter in
  `capabilities/dafny/` proves "every Bump increments count by 1",
  and the Sealer in `jesc24/sealer/dafny/` proves cross-sealer
  unsealability at compile time. Best when the proof side actually
  matters more than the JS shape, and you're willing to write a source
  patch for FFI.

- **Coq** has the most mature proof story (tactic automation, `nia`,
  `auto`, `ring`, decades-old stdlib) and the deepest theorem-proving
  toolkit. Its JS output is the largest by a wide margin (~60 KB
  runtime, mangled identifiers, no library surface) because the
  Coq → OCaml → js_of_ocaml pipeline pays for the OCaml-runtime tax.
  Runs in a vanilla SES Compartment with the right endowments; does
  *not* run through `@endo/import-bundle`. Best when you need the
  proof rigor or you're already in an OCaml-extraction workflow;
  worst for JS-host integration.

For the specific use case "I want to write a verified library and
call it from regular JavaScript (or a SES tenant)":
**Agda for the library case, Idris2 for the SES-embedded-evaluator
case, Dafny when you need verified state machines, Coq when proof
rigor + tactic automation matter more than JS shape.**

## How to reproduce

```sh
nix develop                   # or have dafny / agda / idris2 / coq / ocaml / js_of_ocaml / nodejs on PATH
npm install
npm run check                 # build + SES probes + FFI probes + bundle + diff against committed docs/
```

Individual steps and the "add a new problem" workflow are in
[DEVELOPMENT.md](./DEVELOPMENT.md). The capability and OCAP
explorations are run separately — see each subdirectory's README
(e.g. [`capabilities/coq/README.md`](./capabilities/coq/README.md),
[`jesc24/sealer/README.md`](./jesc24/sealer/README.md)).

Files of interest:

- `problems/<problem>/<tool>/<src>` — the verified sources
- `outputs/<problem>/results.json` — raw build / run / SES JSON
- `outputs/ffi-probe.json` — raw FFI probe JSON
- `outputs/bundles.json` — raw bundle / import-bundle JSON
- `outputs/bundles/<problem>/<tool>/` — preprocessed bundle-input directories
- `docs/<problem>.md` — autogenerated per-problem comparison
- `capabilities/<tool>/README.md` — per-language modularization writeup
- `jesc24/<pattern>/README.md` — per-pattern OCAP comparison
