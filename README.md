# Exploring JavaScript compile targets of Dafny, Agda, and Idris2

A small comparison project. For each of three provable problems we have
side-by-side implementations in all three tools, scripts that compile +
run each output, and probes that evaluate the SES (Hardened JavaScript)
compatibility of the generated JS and the ease of calling the verified
functions from external JavaScript.

## Read the findings

Start with [EVALUATION.md](./EVALUATION.md) for the JS-output analysis,
or jump to the [Language comparison](#language-comparison) section below
for a language-level summary. Per-problem side-by-side detail in
[docs/](./docs/).

For a separate capabilities exploration (passing a host function *into*
verified code; the verified module *being* a capability the host holds),
see [capabilities/](./capabilities/) — one writeup per language, no
mechanized comparison, different approaches per language as appropriate.

## Layout

```
problems/
  factorial/        — recursive Nat → Nat with positivity proof
  reverse/          — list reverse with reverse-reverse-identity theorem
  insertion-sort/   — verified sortedness (Agda/Idris2) + multiset preservation (Dafny)
    <each>/dafny/   — Dafny source
    <each>/agda/    — Agda source
    <each>/idris2/  — Idris2 source

generator/
  problems.js       — declares how each impl builds, runs, and where its JS output lives
  build.js          — compile + run every implementation, dump results.json
  ses-check.js      — static + lockdown() + Compartment SES probes
  ffi-probe.js      — try calling the verified `sort` from external JS in each lang
  bundle.mjs        — bundle each impl with @endo/bundle-source, importBundle into a Compartment
  report.js         — render docs/<problem>.md from results.json + bundles.json

outputs/            — autogenerated JSON manifests + bundles/ + ffi-probe.json + bundles.json
docs/               — autogenerated per-problem comparison markdown
EVALUATION.md       — hand-written analysis across all three dimensions
flake.nix           — pins dafny / agda / idris2 / nodejs from nixpkgs
```

## Setup

NixOS / Nix-with-flakes (default):

```
nix develop          # drops you in a shell with dafny, agda, idris2, node
npm install          # bignumber.js (Dafny runtime dep) + ses (the SES package)
```

Otherwise, install Dafny 4.11+, Agda 2.8+, Idris2 0.8+, and Node 22+ by your own means.

## Run the full pipeline

```
node generator/build.js       # compile + run every implementation
node generator/ses-check.js   # lockdown+require + raw Compartment.evaluate probes
node generator/ffi-probe.js   # call the verified `sort` from external JS in each lang
node generator/bundle.mjs     # @endo/bundle-source + @endo/import-bundle into a Compartment
node generator/report.js      # regenerate docs/<problem>.md
```

This regenerates everything under `outputs/` and `docs/`.

## Language comparison

This section is about the source languages themselves — what each is
strong at and where each fights you — based on what we observed while
implementing the three problems in this repo. The JavaScript-output
side of the story is in `EVALUATION.md`.

### Dafny

**Excels at: SMT-backed proof automation, imperative-style verification.**

The most striking thing about Dafny in this exercise was how little proof
code we wrote. The verified insertion sort in
[`problems/insertion-sort/dafny/InsertionSort.dfy`](./problems/insertion-sort/dafny/InsertionSort.dfy)
proves *both* sortedness and full multiset preservation (i.e. it's a
permutation), and the body of the function is the function — the proof
overhead is one `assert xs == [xs[0]] + xs[1..];` hint plus an
expanded `assert Sorted(...) by { … }` block. The multiset reasoning is
discharged automatically: Dafny's built-in `multiset` type and SMT
encoding handle the algebra (`multiset(a + b) == multiset(a) +
multiset(b)`) without us writing a lemma. Contrast this with Agda/Idris2,
where we punted multiset preservation entirely because constructive
proofs of permutation are nontrivial without a stdlib for it.

Dafny also handles arithmetic, quantifier reasoning, and loop invariants
in stride — `factorial(n) >= 1` needed zero proof annotations beyond the
`ensures` clause. The triangular-number closed form
[`problems/sum-formula/dafny/SumFormula.dfy`](./problems/sum-formula/dafny/SumFormula.dfy)
is the sharpest example: Dafny proves `2 * Σ n = n·(n+1)` in
**four lines of body**, while the Agda port needs ~60 lines because
nothing about commutativity, associativity, distributivity, or `*`
comes pre-proven and the nixpkgs Agda install ships only the bare
`Agda.Builtin.*` modules.

**Doesn't handle well: producing JS you'd want to call from outside.**

The generated JS for our factorial (30 LOC source) is 32 KB, dominated
by a ~600-line runtime prelude (Seq class, BigNumber helpers, Unicode
tables) that gets re-emitted into every output file. Top-level
declarations are module-scoped `let`s rather than `module.exports`, so
the symbols aren't reachable after `require()` (see
[`generator/ffi-probe.js`](./generator/ffi-probe.js) — the Dafny case
has to do source-text surgery to promote those `let`s to `globalThis`).
Integer parameters must be wrapped in `BigNumber`, sequences in
`_dafny.Seq`. None of this is unfixable, but it means Dafny's JS backend
is shaped like a self-running program, not a library.

The other weak spot is debugging when the SMT solver *can't* solve. We
hit this on the insertion-sort Sorted-preservation proof: the failure
mode is "postcondition could not be proved on this return path" with no
counterexample, and progress comes from adding `assert … by { … }`
blocks until the verifier follows along. When it works it's magic; when
it doesn't it's opaque.

### Agda

**Excels at: elegant constructive proofs, decision procedures via inductive families, dependent types.**

The Agda insertion sort at
[`problems/insertion-sort/agda/InsertionSort.agda`](./problems/insertion-sort/agda/InsertionSort.agda)
is the proof I'd pick to *teach* the technique. The `Sorted` and `_≤*_`
families read like inference rules, `with`-abstraction lets the proof
case-split on `compare x y` and refine on the same scrutinee in one
breath, and the `insert-sorted` lemma is six lines with no rewrite
tactics. The proof terms are values that compute — you can normalize a
proof and inspect it.

For propositional reasoning (the `reverse(reverse xs) ≡ xs` theorem in
[`problems/reverse/agda/Reverse.agda`](./problems/reverse/agda/Reverse.agda)),
the standard `rewrite ... | ...` chain is concise and easy to follow.
Unicode identifiers (`≤*`, `∷`, `≡`) keep the math-paper resemblance.

The dependent-vector showcase
[`problems/vec-zipwith/agda/VecZipWith.agda`](./problems/vec-zipwith/agda/VecZipWith.agda)
is the other side of the same strength: `zipWith` over `Vec A n`
has exactly two cases (`[] []` and `(x∷xs) (y∷ys)`) because the type
already rules out length mismatches. The Dafny equivalent has to
encode that guarantee as a runtime precondition every caller is
obligated to discharge.

**Doesn't handle well: producing executables and interop with the outside world.**

Agda is a proof assistant first and a programming language second, and
the JS backend reflects that. Every top-level definition becomes a
*curried* arrow chain on `exports`, with `null` placeholders for each
type-parameter slot, so a host call to `sort` looks like
`exports.sort(null)(xs)` rather than `exports.sort(xs)`. The
multi-file emission (one `jAgda.<Mod>.js` per Agda module, plus
`agda-rts.js`) means using the result requires either a bundler or
careful `NODE_PATH` configuration.

`{-# COMPILE JS … #-}` is a clean inline-FFI mechanism (we relied on it
for every demo's `putStrLn`), but it's per-postulate — there's no
"compile this Agda function with a non-curried JS signature" knob.

Smaller papercut: requiring an Agda module *executes* its embedded `main`
as a side effect because the emitter appends `exports["main"](a => ({}))`
at the bottom of the entry file. Easy to strip, easy to forget.

### Idris2

**Excels at: practical dependently-typed programming, FFI-in, readable output.**

Idris2 is the only one of the three that *also* feels like a general
programming language. The source files look like Haskell with optional
dependent types — list literals (`[3, 1, 4, 1, 5, 9, 2, 6]`),
`do`-notation for `IO`, `printLn` from a real Prelude, `import Data.Nat`
to pull in `LTE` and friends. The 22-line factorial source is the
shortest of the three.

The generated JS at
[`problems/insertion-sort/idris2/build/exec/insertionsort`](./problems/insertion-sort/idris2/) (regenerable)
is the most reader-friendly: named functions (`InsertionSort_insert`),
small tagged-object constructors (`{a1, a2, h}`), `switch (x.h)` for
data-type dispatch, no curried boilerplate. It's the only one of the
three that runs unmodified in a SES `Compartment.evaluate(source)`.

`%foreign "javascript:lambda: x => ..."` is the cleanest inline FFI
syntax of the three — it composes with the type system (you state the
Idris2 type and the JS expression, and Idris2 wires them up).

For proofs that *do* need stdlib support, Idris2 typically beats Agda
because `Data.Nat` ships the algebraic lemmas (`multCommutative`,
`multDistributesOverPlusLeft`, …). The closed-form proof in
[`problems/sum-formula/idris2/SumFormula.idr`](./problems/sum-formula/idris2/SumFormula.idr)
is a 5-line rewrite chain that finishes the same theorem Agda needs
~60 lines (and seven from-scratch lemmas) to close.

**Doesn't handle well: dependent-proof ergonomics (QTT erasure), library exports for JS callers.**

Idris2's Quantitative Type Theory means implicit arguments are
runtime-erased by default. We tripped on this twice in
[`problems/insertion-sort/idris2/InsertionSort.idr`](./problems/insertion-sort/idris2/InsertionSort.idr):
constructing `LTEZero : LTE Z n` inside `lteTrans` failed with "n is not
accessible in this context" because the index `n` (which had to unify
with the goal's `c`) had been erased. The fix — annotating implicits
with `{0 a, b, c : Nat}` and pattern-matching at the right places — is
the right answer once you know QTT, but it's a sharp difficulty cliff
that Agda just doesn't have. (The original first-try `lbTrans` failed
in the same way; final version needed `{0 x, y : Nat}` annotations.)

The other weak spot is symmetric to Agda's but worse: there is no clean
way to *export* a verified Idris2 function for a JS host to call. The
`--cg node` backend produces an executable, not a module — the file
ends with `try { __mainExpression_0() } catch (e) { … }` and the
functions you wrote live inside that script with mangled names but no
`module.exports`. Our FFI probe extracts `sort` by reading the file as
text, stripping the main invocation, and `new Function()`-ing the rest
(see [`generator/ffi-probe.js`](./generator/ffi-probe.js)). Workable,
but Agda's `require('./jAgda.X.js').sort(...)` it ain't.

### One-line summary

| | Dafny | Agda | Idris2 |
| --- | --- | --- | --- |
| **Best at** | automated proofs over imperative code; algebraic reasoning | elegant constructive proofs; dependent types as the only abstraction tool | dependently-typed *programming* with a clean FFI; concise rewrites against `Data.Nat` |
| **Worst at** | producing JS you can call as a library; expressing dependent types | producing executables / non-curried JS APIs; ad-hoc arithmetic without a stdlib | dependent-proof ergonomics under QTT erasure; exporting symbols for JS hosts |
| **See it in:** | `insertion-sort/dafny/*` (auto-discharged multiset), `sum-formula/dafny/*` (4-line proof) | `insertion-sort/agda/*` (clean inference rules), `vec-zipwith/agda/*` (no length-mismatch case) | `vec-zipwith/idris2/*` (same Vec elegance), `sum-formula/idris2/*` (5-line rewrite chain) |

Pick Dafny when you want to push proof obligations through an SMT
solver. Pick Agda when the proof is the artifact and you want it to
read like mathematics. Pick Idris2 when you want a dependently-typed
program that compiles to JS you'd actually be willing to ship.
